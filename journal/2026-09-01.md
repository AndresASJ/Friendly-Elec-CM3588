# 2026-09-01 — Import blocked by toshiba permissions; indexer→client routing was never wired up

Follow-on from `journal/2026-08-31.md`. With Jellyseerr fixed, three further faults
surfaced in the same download path.

## 1. Radarr grabbed a 44 GB remux with 3 seeders

The first Hamilton grab was `Hamilton.2020.NORDiC.1080p.BluRay.REMUX...`, 44 GB with
3 seeders — ETA **35 days**, 0.38 GB moved in an hour. Not a fault as such: the
`HD-1080p` profile scores `Remux-1080p` top, so Radarr took the technically-best
release regardless of swarm health.

Every better option was being rejected with *"Quality for release in queue already
meets cutoff"* — i.e. rejected **because** the remux was already queued. Removing +
blocklisting it freed the field:

```
Hamilton.2025.BluRay.1080p.DDP.Atmos.5.1.x264-hallowed   13 GB, 127 seeders
```

Same `hallowed` group as previous good grabs, on seedpool. Finished in ~40 minutes.

**Worth considering:** nothing in the profile weighs seeder count, so this will recur
on any title where the remux is a dead swarm.

## 2. qBit queueing was disabled — 53 torrents all running at once

```
"queueing_enabled": false      "max_active_downloads": 4   ← inert
```

All 53 torrents ran concurrently, splitting ~25 MB/s ~53 ways, and torrent priority
had no effect (no queue to order). Enabled queueing, with seeding deliberately
uncapped so private-tracker ratio is never throttled:

```
queueing_enabled=true  max_active_downloads=4
max_active_uploads=-1  max_active_torrents=-1   (-1 = unlimited)
dont_count_slow_torrents=true
```

`max_active_torrents=-1` matters: queueing counts *seeding* torrents toward the cap,
so a finite value would have paused seeders to make room for downloads — silently
undercutting the seeding policy.

## 3. Imports failed — `/mnt/toshiba` media dirs were root-owned  ← the real blocker

Hamilton downloaded 100%, then Radarr sat at `importBlocked`:

```
System.UnauthorizedAccessException: Access to the path
'/data/media/movies/Hamilton (2025)' is denied.
```

Radarr/Sonarr run as **uid 1000** (`PUID=1000`; note `docker exec radarr id` reports
root and is misleading — check the *process* owner, `ps -o user -C Radarr`).

Branch permissions had drifted apart:

| branch | `data/media/movies` |
|---|---|
| drive1 / drive3 / drive4 | `drwxrwsrwx 1001:1002` ✅ |
| **toshiba** | **`drwxr-xr-x root:root`** ❌ |

mergerfs uses `category.create=mfs` (most free space) and toshiba is now the emptiest
branch (1021 G free vs drive2's 816 G), so **every new library folder was being
created on toshiba** — and uid 1000 cannot write a root-owned 755 dir. Fixed to match
the other branches:

```bash
chown root:1002  /mnt/toshiba/data /mnt/toshiba/data/media
chmod 2755       /mnt/toshiba/data /mnt/toshiba/data/media
chown 1001:1002  /mnt/toshiba/data/media/{movies,shows}
chmod 2777       /mnt/toshiba/data/media/{movies,shows}
```

Only those four parent dirs were wrong — existing children were already `1001:1002`.
This was **not** Hamilton-specific: it would have blocked every import, TV included,
for as long as toshiba stayed the most-free branch. Shows kept importing until now
only because toshiba became emptiest recently.

Verified after the fix — hardlink intact, so the pool is doing its job:

```
links=2  inode=16973291707844871429   media/movies/Hamilton (2025)/...mkv
links=2  inode=16973291707844871429   torrents/complete/...mkv
```

Jellyfin then needed only a `POST /Library/Refresh` to show it.

## 4. Private/Public download clients were never actually routed

The split was **decorative**. Both clients sat at `priority=1` with `tags=[]`, and
every indexer had `downloadClientId=0` ("any"), so Sonarr/Radarr round-robined:
seedpool grabs landing in the *public* category, 1337x grabs in the *private* one,
alternating. Of 53 live torrents, **20 were wrong** — 11 private-tracker torrents
categorised public (deleted on import, losing seed time and buffer) and 9 public
torrents categorised private (seeded 14 days, against the seeding policy).

Fixed by pinning each indexer to its client (`downloadClientId`), using Prowlarr's
own `privacy` field as the source of truth:

| indexer | privacy | client |
|---|---|---|
| seedpool, DigitalCore | private | `qBittorrent - Private` (id 1) |
| 1337x, YTS | public | `qBittorrent - Public` (id 2) |

**Client *tags* are the wrong tool here** — in Sonarr/Radarr those match against
series/movie tags, not the indexer. `downloadClientId` on the indexer is the only
thing that routes by source.

Prowlarr syncs these indexers at `syncLevel=fullSync`, so the obvious worry was that
it would reset the field. Tested by forcing `ApplicationIndexerSync` and re-reading
both apps: **the setting survives**. The 20 mislabelled live torrents were then
re-categorised in place (all four *arr categories have an empty `savePath`, so
nothing moved on disk).

## 5. `qbit-cleanup.py` back on a schedule, with a new guard

It had not run since **2026-06-14** — it was a one-shot that removed its own crontab
line via `--from-cron`, and `/var/log/qbit-cleanup.log` was empty. Re-scheduled
*without* that flag:

```cron
30 4 * * * /usr/bin/python3 /usr/local/bin/qbit-cleanup.py --apply >> /var/log/qbit-cleanup.log 2>&1
```

Two corrections to the script first (backup: `qbit-cleanup.py.bak-*`):

- **Added `DEAD_MIN_AGE = 24h`.** Rule (c) removes `stalledDL` torrents under 100%.
  With queueing now enabled a freshly-grabbed torrent legitimately sits at 0%
  awaiting a slot — the dry run flagged **4 Last Ship torrents added minutes earlier**
  as "dead". Unguarded, the first cron run would have deleted live grabs.
- **Corrected the header's "there are NO hardlinks" claim**, false since the pool
  migration. Deletion is still safe (dropping one link leaves the library's), but the
  reported *reclaimable GB* is an over-estimate — freeing a hardlinked torrent
  returns ~0 bytes.

First live run removed 1 public imported torrent (The Rehearsal S01, 6 GB);
confirmed Sonarr still lists 12 episode files on disk afterwards.
