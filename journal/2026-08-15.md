# 2026-08-15 — Silent qBit VPN death (wedged NAT-PMP) + PlexAmp removed

## Summary
Full stack review. Found qBittorrent had been firewalled with zero traffic for
~3 days after gluetun's ProtonVPN NAT-PMP port-forwarding loop wedged, while the
WireGuard tunnel itself stayed up (so gluetun kept reporting `healthy`).
Restarted the tunnel to recover. Also removed PlexAmp, which had been in a crash
loop since March with 61,969 restarts.

## Changes
- Restarted `gluetun-qbit`, then `qbittorrent` (it shares gluetun's netns via
  `network_mode: service:gluetun`, so it needs its own restart afterwards).
- Removed PlexAmp: `docker compose down` in `/var/lib/casaos/apps/plexamp`,
  then deleted that directory so it disappears from the CasaOS UI.
  Config (`/DATA/AppData/plexamp`, 64K) left in place; it holds no claim token.

## Why
**qBit VPN.** At `2026-08-12 22:40:38` gluetun lost its NAT-PMP session:

```
ERROR [port forwarding] adding port mapping: executing remote procedure call:
  reading from udp connection: read udp 10.2.0.2:42861->10.2.0.1:5351: recvfrom: connection refused
INFO  [port forwarding] starting
```

It logged `starting` and then never logged again — the port-forwarding goroutine
never came back. `/tmp/gluetun/forwarded_port` was truncated to 0 bytes and stayed
that way. Result: `connection_status=firewalled`, `listen_port=0`, `dht_nodes=0`,
151 torrents `stalledUP` and 7 `stalledDL` at 0 B/s for three days.

After the restart: new server, public IP 163.5.171.126 (Secaucus NJ), forwarded
port 54316, `connection_status=connected`, 263 DHT nodes, ~1.6 MB/s up immediately.

**PlexAmp.** Deployed 2026-03-10 with an empty `PLEXAMP_CLAIM_TOKEN`. Claim tokens
from plex.tv/claim are single-use and expire in 4 minutes, so it never completed
first-start auth — `Error exchanging claim token` on every boot, `restart:
unless-stopped` looping it roughly every 55 seconds ever since. Not used; removed
rather than re-claimed.

## Gotchas
- **`gluetun` reporting `healthy` does NOT mean port forwarding works.** The
  healthcheck (`HEALTH_TARGET_ADDRESSES=cloudflare.com:443,github.com:443`) only
  proves the tunnel carries traffic. Port forwarding is a separate loop that can
  die silently while the container stays green. `HEALTH_RESTART_VPN=on` does not
  cover it. This is exactly the failure mode `vpn-healthcheck.sh` was written for
  on 2026-05-31, and it was the only thing that caught it.
- **`vpn-healthcheck.sh` alerts on transition only, then goes quiet.** It fired
  once on 08-12 and then logged `status=DOWN prev=DOWN` every 5 minutes for three
  days without re-alerting. Correct by design (no alert spam), but a single missed
  Telegram message means three days of downtime. Worth adding a re-alert after N
  consecutive DOWN checks, or auto-remediation.
- **The port-push scripts were never broken** — worth recording, since the logs
  make them look broken. Both `qbit-port-forward.sh` (gluetun's native
  `VPN_PORT_FORWARDING_UP_COMMAND`) and the `*/5` cron `update-port.sh` throw
  `setPreferences ... [1]` / `Connection refused` when they fire while qBit's WebUI
  isn't listening yet — normal during startup ordering. Both verified working:
  gluetun's hook pushed 54316 into qBit automatically, and the cron script returns
  `Port updated to 54316`. qBit has `bypass_local_auth: true`, so localhost calls
  need no credentials.
- The two port-push mechanisms are redundant (the cron predates the native hook).
  Harmless, but only one is needed.

## Open items
- `update-port.sh` contains the qBit WebUI password in plaintext and is `0755`.
  Not in the repo, local exposure only. Should be `0600`, or dropped entirely in
  favour of gluetun's native hook.
- `drive1` at 96% (83G free) and `drive3` at 93% (133G free). `drive1` is the
  Docker data-root *and* containerd store *and* 1.1T of torrents — same class of
  risk as the June eMMC incident. The 1.8T Toshiba is at 3% used.
- PlexAmp's leftover config dir `/DATA/AppData/plexamp` can be deleted whenever.
